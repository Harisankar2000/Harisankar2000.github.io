One microservice needs to connect to 5 databases. How do you manage that, and what are the optimised ways to do it?design

Short answer: "First I'd ask why it needs five. If they are different kinds of store, each doing its own job (Postgres for transactions, ClickHouse for analytics, Redis for cache, and so on), that is normal polyglot persistence. I'd create one connection pool per database at startup, size the pools so they fit the database's connection limits, hide each database behind a repository layer, and keep the data consistent with events instead of distributed transactions. If the service reads other services' databases directly, that is a design smell, and I'd call their APIs instead."

Step 1: ask which case it is. The right answer depends on it.

CaseExampleApproach
Different kinds of database, each for its own jobPostgres (loans), ClickHouse (telemetry), Redis (cache, locks), MongoDB (documents), Elasticsearch (search)Fine. One client and pool per database, with a repository layer for each.
Same database engine, several instancesPrimary plus read replicas, shards, or one database per tenantRoute queries: writes go to the primary, reads to replicas. Keep a map of tenant to pool.
Other services' databasesThe loan service reading the user service's tablesShared-database anti-pattern. Call the owning service's API, or consume its events and keep a local read copy.

Step 2: optimisations to talk about.

  1. One pool per database, created once. Create clients at boot, not per request. Reuse them through Fastify decorators or NestJS providers. Close them all on SIGTERM.
  2. Pool sizing. pool size × number of pods ≤ the database's max_connections, with some headroom. With 10 pods and a pool of 20, you already use 200 Postgres connections. Put PgBouncer or RDS Proxy in front of Postgres if pods autoscale.
  3. Bulkhead isolation. Separate pools mean a slow ClickHouse query can't use up the connections Postgres needs. Add a timeout for each database and a circuit breaker, so if one database is down only the features that use it fail, not the whole service.
  4. Repository layer. Business logic calls loanRepo.findById() and telemetryRepo.latest(). It never touches raw clients. You can then swap or mock databases, and tests stay simple.
  5. Read/write split. Send writes to the primary and heavy reads to replicas. Watch replication lag: read your own writes from the primary.
  6. Run independent queries in parallel. Promise.all([pg.query(...), ch.query(...)]) when one doesn't depend on the other. Total latency is then the slowest query, not the sum of all of them.
  7. Cache in Redis for hot, rarely changing reads, so fewer requests reach the expensive databases.
  8. Consistency without distributed transactions. Avoid 2PC across five databases. Make one database the source of truth (usually Postgres). Use the transactional outbox or CDC (Debezium) to publish changes to Kafka, and let consumers update ClickHouse, Elasticsearch and the cache. Use a saga with compensating actions for multi-step workflows. Make every consumer idempotent.
  9. Database per tenant. Keep a pool for each tenant in an LRU map keyed by tenantId. Close pools that have been idle, so 500 tenants don't hold 500 open pools. An alternative is schema-per-tenant on one database, using search_path.
  10. Lazy connect for databases that are rarely used, and use health checks (readiness probe) that report each database separately.
  11. Configuration and secrets for each database come from environment variables or a secret manager. Never hard-code them.
  12. Observability: per-database metrics (pool in use or waiting, query latency, errors) so you can tell which database is causing trouble.

A huge number of requests arrive at once on a webhook. How do you handle that? What are the best practices?design

Short answer: "Accept fast and process later. The webhook endpoint only verifies the signature, stores the event in a durable queue and returns 200 in a few milliseconds. Workers then process from the queue at a rate the database can handle, with idempotency on the provider's event ID, retries with backoff, and a dead-letter queue. The queue absorbs the spike, and the ingestion layer scales horizontally."

Flow:

Provider ──► Load balancer / API Gateway (rate limit, body size limit)
           ──► Webhook receiver (stateless, autoscaled)
                 1. verify HMAC signature on the raw body
                 2. dedupe on event_id (Redis SET NX)
                 3. push to queue (Kafka / BullMQ / SQS) + store the raw payload
                 4. return 200 immediately
           ──► Queue (buffer: absorbs the spike)
           ──► Workers (controlled concurrency, batching)
                 → DB / downstream APIs
           ──► Retries with backoff → DLQ → alert

Best practices:

  1. Respond fast. Do no heavy work in the request. Providers time out (often 5–30 s) and retry, and slow responses turn a spike into a retry storm.
  2. Durable queue as a buffer. Kafka for very high volume and ordering, BullMQ (Redis) for job-style work, or SQS (API Gateway → SQS → Lambda gives you a serverless version). Return 200 only after the event is safely enqueued. If the queue is down, return 503 so the provider retries later. Never acknowledge an event you might lose.
  3. Idempotency. Providers deliver at least once, so you will get duplicates. Dedupe on the provider's event ID: SET webhook:{id} 1 NX EX 86400 in Redis, plus a unique constraint in the database as the final guard.
  4. Control the processing rate, not the arrival rate. Set worker concurrency, use the BullMQ limiter, and size the database pool to protect the database and third-party APIs. The queue absorbs the backlog, and you watch queue lag.
  5. Batching. Workers write in batches (for example 500 rows or 1 s) instead of one insert per event.
  6. Ordering where it matters. Use a Kafka partition key such as loanId, so events for the same entity are processed in order. Also guard with a state machine: only move state forward, and ignore "pending" if "success" was already applied.
  7. Retries and DLQ. Use exponential backoff with jitter. After N attempts, move the event to a dead-letter queue, alert, and provide a replay tool.
  8. Store the raw payload (Postgres or S3) before processing, for audit, debugging and replay.
  9. Scale horizontally. Run stateless receivers behind a load balancer, autoscale on CPU or request rate, and scale workers on queue length (KEDA in Kubernetes).
  10. Security. HMAC signature over the raw body, a timestamp check (reject anything older than 5 minutes to stop replays), an IP allowlist if the provider publishes IPs, a body size limit, and rate limiting at the gateway.
  11. Reconciliation. Webhooks can be missed. Run a scheduled job that polls the provider's API for anything still pending. For money, re-fetch the status from the provider before marking something as paid.
  12. Monitoring: requests per second, p99 response time, queue depth and lag, DLQ size, and duplicate rate.

Fastify + BullMQ receiver:

const crypto = require('crypto');
const { Queue } = require('bullmq');
const queue = new Queue('webhooks', { connection: redis });

app.post('/webhooks/payments', { config: { rawBody: true }, bodyLimit: 1048576 }, async (req, reply) => {
  const sig = req.headers['x-signature'];
  const expected = crypto.createHmac('sha256', process.env.WEBHOOK_SECRET).update(req.rawBody).digest('hex');
  if (!sig || !crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expected))) {
    return reply.code(401).send();
  }

  const eventId = req.body.id;
  const fresh = await redis.set(`wh:${eventId}`, '1', 'NX', 'EX', 86400);
  if (!fresh) return reply.code(200).send({ duplicate: true });

  await queue.add('payment-event', req.body, {
    jobId: eventId,                       // BullMQ also dedupes on jobId
    attempts: 5,
    backoff: { type: 'exponential', delay: 2000 },
    removeOnComplete: true,
  });
  return reply.code(200).send({ received: true });
});

// worker.js
new Worker('webhooks', async (job) => processPaymentEvent(job.data), {
  connection: redis,
  concurrency: 20,

What is Kubernetes, and what is it best used for?theory

Short answer: "Kubernetes is a container orchestrator. You declare the desired state (for example, run 5 replicas of this image with this much CPU and memory) and its controllers keep reconciling the actual state to match: restarting crashed containers, rescheduling them when a node dies, scaling on load and rolling out new versions with zero downtime. It is best for running many containerised microservices that need autoscaling, self-healing and consistent deployments."

Docker vs Kubernetes: Docker builds and runs a container on one machine. Kubernetes runs and manages many containers across a cluster of machines.

Where Kubernetes is the best fit:

  • Many microservices that need one standard way to deploy, configure, discover and scale them.
  • Autoscaling: the HPA scales pods on CPU, memory or custom metrics. KEDA scales on Kafka lag or queue length, which is ideal for consumers and workers. The Cluster Autoscaler adds nodes.
  • Self-healing: liveness probes restart stuck pods, and readiness probes take a pod out of the load balancer until it is ready.
  • Zero-downtime deploys: rolling updates, instant rollback (kubectl rollout undo), and canary or blue-green deploys with tools like Argo Rollouts.
  • Service discovery and load balancing: services call each other by name (http://loan-service).
  • Config and secrets separate from the image (ConfigMap, Secret).
  • Efficient resource use: packs many services onto fewer machines using CPU and memory requests and limits.
  • Portability: the same manifests run on EKS, GKE, AKS or on-prem, and the same setup works for dev, staging and prod.
  • Batch work: Jobs and CronJobs for exports, reconciliation and reports.

When not to use it: a small team with a few services (ECS/Fargate, App Runner, Lambda or Docker Compose on EC2 is simpler and cheaper), purely event-driven or spiky workloads (Lambda), and databases (prefer a managed service like RDS over running them yourself in Kubernetes). Kubernetes has real operational cost: upgrades, networking, security and YAML sprawl.

What is NestJS? Why use it instead of Express or Fastify, and what is its best use case?theory

Short answer: "NestJS is an opinionated, TypeScript-first framework for Node, inspired by Angular and Spring. It isn't really instead of Express or Fastify: it runs on top of them (Express by default, Fastify through an adapter). What it adds is structure: modules, dependency injection, decorators, and a standard request pipeline with guards, pipes, interceptors and filters, plus built-in support for microservices, GraphQL, WebSockets, queues and Swagger. Express and Fastify give you routing and leave the architecture to you. Nest gives you the architecture, which pays off in large codebases with many developers."

Building blocks:

  • Module (@Module): groups related controllers and providers, such as LoanModule and AuthModule.
  • Controller (@Controller, @Get, @Post): handles routes.
  • Provider / Service (@Injectable): business logic, injected through the constructor.
  • Dependency injection container: Nest creates and wires dependencies. In tests you override a provider with a mock.
  • Middleware: the same as Express middleware.
  • Guards (CanActivate): authentication and RBAC. They decide whether a request may proceed.
  • Pipes: validation and transformation (ValidationPipe with class-validator DTOs, or a Zod pipe).
  • Interceptors: code that runs before and after the handler: logging, response mapping, caching, timeouts.
  • Exception filters: turn errors into consistent HTTP responses.

Request lifecycle (often asked): Middleware → Guards → Interceptors (before) → Pipes → Controller handler → Interceptors (after) → Exception filters (if anything throws).

Why choose NestJS:

  • A large team gets one consistent structure: any developer can open any module and know where things are. That means less "Express spaghetti".
  • DI makes unit testing easy: Test.createTestingModule with overrideProvider.
  • Cross-cutting concerns (auth, validation, logging, error format) are written once as guards, pipes, interceptors and filters, and applied with a decorator.
  • Batteries included: @nestjs/config, @nestjs/swagger (docs generated from DTOs), @nestjs/bullmq, @nestjs/schedule, @nestjs/terminus (health checks), @nestjs/graphql, @nestjs/websockets, @nestjs/cqrs, plus TypeORM, Prisma and Mongoose integrations.
  • Microservices: the same handler style over many transports (@MessagePattern for request/response, @EventPattern for events).

Best use cases: enterprise backends with many domains (lending, banking, ERP), microservice systems with Kafka, Redis or gRPC between them, teams coming from Java Spring or Angular, and long-lived products where maintainability matters more than raw speed.

When not to use it: tiny services or scripts, Lambda functions where cold start matters (Nest's DI bootstrap adds startup time), and extremely hot paths where you want raw Fastify. Downsides: learning curve, decorator "magic" that is harder to debug, more boilerplate, and circular dependency problems between modules (forwardRef is a sign the design needs fixing).

Indexing: composite and partial indexes

What is a composite index? How do you choose the column order?theory

Short answer: "A composite (multi-column) index is one B-tree index on several columns, sorted by the first column, then by the second inside it, and so on, like a phone book sorted by surname then first name. It helps any query that uses a leftmost prefix of its columns. I put equality columns first, then the range or sort column, so one index can both filter and return rows already in order."

CREATE INDEX idx_loans_org_status_created
  ON loans (org_id, status, created_at DESC);
QueryUses the index?Why
WHERE org_id = 7YesLeftmost column
WHERE org_id = 7 AND status = 'PENDING'YesLeftmost two columns
WHERE org_id = 7 AND status = 'PENDING' ORDER BY created_at DESC LIMIT 20Yes, best caseFilters and reads rows already sorted. No separate sort step.
WHERE org_id = 7 AND created_at > now() - interval '7 days'PartlyUses org_id, then scans all statuses within that org
WHERE status = 'PENDING'Usually noSkips the leading column. Postgres may do a full index scan, which is rarely worth it.
WHERE created_at > ...NoSkips the leading columns

Rules for column order:

  1. Equality columns first (=, IN), then one range or sort column last (>, BETWEEN, ORDER BY). After a range column, later columns can't be used for seeking.
  2. Among equality columns, put the one every query has first (often org_id in a multi-tenant app), so more queries can share the index.
  3. Match the sort direction your query uses (created_at DESC) if it mixes directions, e.g. ORDER BY a ASC, b DESC.

Covering index (index-only scan): add extra columns that are only returned, not filtered, with INCLUDE. Postgres can then answer from the index without visiting the table.

CREATE INDEX idx_loans_org_status_cov
  ON loans (org_id, status) INCLUDE (amount, customer_id);

-- answered from the index alone (if the visibility map is up to date)
SELECT amount, customer_id FROM loans WHERE org_id = 7 AND status = 'SANCTIONED';

Composite vs separate single-column indexes: with separate indexes on org_id and status, Postgres can combine them with a BitmapAnd, but that is slower than one composite index and can't give sorted output. Composite wins for a frequent, known query pattern. Separate indexes are more flexible for ad-hoc filters.

Costs: every index slows down INSERT/UPDATE/DELETE, uses disk and memory, and prevents HOT updates when an indexed column changes. An index on (a, b) already covers queries on a alone, so a separate index on a is redundant. Check usage with pg_stat_user_indexes.idx_scan and drop indexes nobody uses.

Prove it with EXPLAIN:

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM loans WHERE org_id = 7 AND status = 'PENDING'
ORDER BY created_at DESC LIMIT 20;
-- good:  Index Scan using idx_loans_org_status_created ... (no Sort node)
-- bad:   Seq Scan on loans ... -> Sort

Prisma: @@index([orgId, status, createdAt(sort: Desc)]) in the model.

What is a partial index? Give real examples.theory

Short answer: "A partial index has a WHERE clause, so it only contains the rows that match. It's smaller, faster to scan and cheaper to maintain than indexing the whole table. I use it when queries only ever look at a small, well-defined subset, like pending jobs or rows that aren't soft-deleted, and for conditional uniqueness rules."

Example 1: hot subset. A jobs table has 50 million rows, but only a few thousand are PENDING. Workers only ever query the pending ones.

CREATE INDEX idx_jobs_pending ON jobs (run_at) WHERE status = 'PENDING';

-- uses the tiny index
SELECT * FROM jobs WHERE status = 'PENDING' AND run_at <= now()
ORDER BY run_at LIMIT 100 FOR UPDATE SKIP LOCKED;

Example 2: unique only among live rows (soft delete). Email must be unique, but a deleted user's email can be reused.

CREATE UNIQUE INDEX uq_users_email_live ON users (lower(email)) WHERE deleted_at IS NULL;

Example 3: business rule enforced by the database. A customer can have only one active loan application at a time.

CREATE UNIQUE INDEX uq_one_active_loan ON loan_applications (customer_id)
  WHERE status IN ('LEAD', 'CREDIT', 'QC', 'SANCTION');
-- a second active application fails with 23505 unique_violation, even if two requests race

Example 4: skip NULLs or a dominant value. CREATE INDEX ON payments (failure_code) WHERE failure_code IS NOT NULL; If 99% of rows are NULL, indexing them is wasted space.

The catch: the planner only uses a partial index if it can prove the query's WHERE implies the index's predicate. WHERE status = 'PENDING' works. WHERE status = $1 with a generic prepared-statement plan may not, because the planner doesn't know the value. Write the condition literally, or check with EXPLAIN.

Other index types worth naming: expression index (ON users (lower(email))), GIN for JSONB, arrays and full-text search, BRIN for huge append-only tables ordered by time (tiny, good for telemetry logs in Postgres), hash for equality only.

Prisma note: Prisma's schema doesn't express partial indexes everywhere, so add them in a SQL migration (prisma migrate dev --create-only, then edit the SQL).

How do you add an index to a big production table without downtime?theory

Short answer: "A plain CREATE INDEX takes a SHARE lock that blocks all writes until it finishes, which can take minutes on a big table. I use CREATE INDEX CONCURRENTLY: it builds without blocking writes, takes longer, and can't run inside a transaction. If it fails it leaves an INVALID index that I drop and retry."

SET lock_timeout = '5s';
CREATE INDEX CONCURRENTLY idx_loans_org_status ON loans (org_id, status);

-- check for a failed build
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
DROP INDEX CONCURRENTLY idx_loans_org_status;   -- then retry

Same idea for other schema changes: ALTER TABLE takes an ACCESS EXCLUSIVE lock. Set lock_timeout so a migration waiting behind a long query doesn't freeze every other query queued behind it. Add constraints as NOT VALID, then VALIDATE CONSTRAINT separately.

Locking and deadlocks

What types of locks are there in PostgreSQL? Explain with examples.theory

Short answer: "There are three families. Table-level locks, which every statement takes automatically and which matter mostly for DDL. Row-level locks, taken by UPDATE, DELETE and SELECT ... FOR UPDATE/SHARE. And advisory locks, which the application takes on a number it chooses. Because of MVCC, plain reads take no row locks: readers never block writers and writers never block readers."

1. Shared vs exclusive: the basic idea. A shared (S) lock lets many transactions read together. An exclusive (X) lock lets only one transaction change the data. S is compatible with S. X conflicts with everything.

2. Row-level locks (strongest to weakest):

LockTaken byBlocks
FOR UPDATEDELETE, UPDATE of a key column, SELECT ... FOR UPDATEAll other row locks and writes on that row
FOR NO KEY UPDATEPlain UPDATE of non-key columnsOther updates and FOR SHARE, but not FOR KEY SHARE (so FK checks still pass)
FOR SHARESELECT ... FOR SHAREWriters. Other FOR SHARE readers can share it.
FOR KEY SHAREForeign key checks: inserting a child row locks the parent row this wayOnly deleting the parent or changing its key

3. Table-level locks (the ones worth naming):

Lock modeTaken byConflicts with
ACCESS SHARESELECTOnly ACCESS EXCLUSIVE
ROW EXCLUSIVEINSERT, UPDATE, DELETESHARE and stronger (so a plain CREATE INDEX blocks writes)
SHARE UPDATE EXCLUSIVEVACUUM, ANALYZE, CREATE INDEX CONCURRENTLYItself and stronger
SHARECREATE INDEX (non-concurrent)Writes
ACCESS EXCLUSIVEALTER TABLE, DROP, TRUNCATE, VACUUM FULLEverything, even plain SELECT

4. Advisory locks: application-defined locks on a number, not tied to a row.

-- only one pod runs the weekly portfolio email job
SELECT pg_try_advisory_lock(hashtext('weekly-portfolio-email'));  -- true for one caller, false for the rest
-- ... do the work ...
SELECT pg_advisory_unlock(hashtext('weekly-portfolio-email'));

-- transaction-scoped version, released automatically at COMMIT/ROLLBACK
SELECT pg_advisory_xact_lock(hashtext('loan:' || $1));

Example of the lock queue trap: a long SELECT holds ACCESS SHARE. A migration's ALTER TABLE asks for ACCESS EXCLUSIVE and waits. Now every new SELECT queues behind the ALTER, and the table looks down. That's why migrations set lock_timeout.

Pessimistic vs optimistic locking. When do you use each? Show code.theory

What is a deadlock? Walk through an example and how you prevent it.theory

Short answer: "A deadlock is when two transactions each hold a lock the other one needs, so both wait forever. Postgres checks for this cycle after deadlock_timeout (1 second by default), kills one transaction with error 40P01, and lets the other finish. I prevent it by always locking rows in the same order, keeping transactions short, and retrying the transaction that got killed."

Step by step: two opposite transfers. A sends 100 to B while B sends 50 to A.

TimeTransaction 1 (A → B)Transaction 2 (B → A)
t1UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
locks row A
t2UPDATE accounts SET balance = balance - 50 WHERE id = 'B';
locks row B
t3UPDATE ... WHERE id = 'B';
waits for T2
t4UPDATE ... WHERE id = 'A';
waits for T1 → cycle
t5continues and commitsERROR: deadlock detected (40P01), rolled back

The four conditions (all must hold for a deadlock): mutual exclusion, hold and wait, no preemption, circular wait. In practice you break circular wait with a consistent lock order.

Prevention:

  1. Lock in a fixed order. Sort IDs and lock them all up front. 
    SELECT id FROM accounts WHERE id IN ($1, $2) ORDER BY id FOR UPDATE;
    Now both transfers try to lock A first. The second one simply waits; there's no cycle.
  2. Keep transactions short. No HTTP calls, KYC requests or Kafka publishes inside a transaction. Use the outbox for events.
  3. Multi-row updates in a fixed order too. UPDATE ... WHERE id IN (...) locks rows in whatever order it scans them. If two batch jobs overlap, lock first with SELECT ... ORDER BY id FOR UPDATE.
  4. Lock the strongest level you'll need up front. Taking FOR SHARE and later upgrading to FOR UPDATE deadlocks when two transactions do it at once.
  5. Index foreign keys and the columns in UPDATE ... WHERE, so statements lock only the rows they need, not large scanned ranges.
  6. Use timeouts so nothing waits forever: lock_timeout, statement_timeout, idle_in_transaction_session_timeout.

Handling: retry with backoff. A deadlock or serialization failure means "try again", not "fail the request".

async function withRetry(fn, attempts = 3) {
  for (let i = 1; ; i++) {
    try {
      return await fn();
    } catch (err) {
      const retryable = err.code === '40P01' || err.code === '40001'; // deadlock, serialization failure
      if (!retryable || i >= attempts) throw err;
      await new Promise(r => setTimeout(r, 20 * 2 ** i + Math.random() * 20)); // jittered backoff
    }
  }
}

await withRetry(() => prisma.$transaction(async (tx) => {
  await tx.$queryRaw`SELECT id FROM accounts WHERE id IN (${from}, ${to}) ORDER BY id FOR UPDATE`;
  await tx.$executeRaw`UPDATE accounts SET balance = balance - ${amt} WHERE id = ${from}`;
  await tx.$executeRaw`UPDATE accounts SET balance = balance + ${amt} WHERE id = ${to}`;
}));

Retry the whole transaction, never just the failed statement: the database already rolled back everything. Make it idempotent (Idempotency-Key) so a retry after a timeout can't double-post.

Can a deadlock happen without explicit locks, for example on INSERT or foreign keys?theory

Short answer: "Yes. Every UPDATE and DELETE locks rows implicitly, foreign key checks take FOR KEY SHARE on the parent row, and inserts into a unique index wait on each other when they insert the same key. So two ordinary-looking transactions can deadlock."

Unique index example:

T1: INSERT INTO wallets (user_id) VALUES (1);   -- ok
T2: INSERT INTO wallets (user_id) VALUES (2);   -- ok
T1: INSERT INTO wallets (user_id) VALUES (2);   -- waits: T2 might commit user 2
T2: INSERT INTO wallets (user_id) VALUES (1);   -- waits for T1 → deadlock

Fix: insert in sorted key order, or use INSERT ... ON CONFLICT DO NOTHING for idempotent upserts.

Foreign key example:

T1: INSERT INTO repayments (loan_id, ...) VALUES (10, ...);  -- FOR KEY SHARE on loan 10
T2: INSERT INTO repayments (loan_id, ...) VALUES (20, ...);  -- FOR KEY SHARE on loan 20
T1: DELETE FROM loans WHERE id = 20;                         -- needs FOR UPDATE on loan 20: waits for T2
T2: DELETE FROM loans WHERE id = 10;                         -- waits for T1 → deadlock

Plain updates of non-key columns take FOR NO KEY UPDATE, which does not conflict with FK checks. So this mostly bites when parents are deleted or their keys change, and when the FK column on the child table has no index (the delete then has to scan the child table).

Other hidden causes: triggers that update another table, ORMs that update rows in a different order per request, and SELECT ... FOR UPDATE without ORDER BY.

How do you find and debug locking problems or deadlocks in production?theory

Short answer: "Turn on log_lock_waits so slow lock waits are logged, and read the deadlock entries in the Postgres log, which show both queries. When something is blocked right now, query pg_stat_activity with pg_blocking_pids() to see who is blocking whom, and look for sessions that are idle in transaction."

-- who is blocked, and by whom
SELECT a.pid, a.state, now() - a.xact_start AS tx_age,
       pg_blocking_pids(a.pid) AS blocked_by, left(a.query, 80) AS query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0;

-- long-running or forgotten transactions holding locks
SELECT pid, state, now() - xact_start AS age, left(query, 80)
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'active') AND xact_start < now() - interval '1 minute'
ORDER BY age DESC;

-- last resort
SELECT pg_cancel_backend(12345);     -- cancel the query
SELECT pg_terminate_backend(12345);  -- kill the session

Settings to mention: log_lock_waits = on (logs waits longer than deadlock_timeout), deadlock_timeout = 1s, lock_timeout, statement_timeout, idle_in_transaction_session_timeout (kills sessions that opened a transaction and forgot to commit, a common Node bug when an error skips ROLLBACK and the client goes back to the pool).

Metrics: count of 40P01 errors, lock wait time, and pool "waiting" counts in your dashboards.

Several workers pick jobs from one table. How do you stop two workers taking the same job? (SKIP LOCKED / NOWAIT)theory

Short answer: "SELECT ... FOR UPDATE SKIP LOCKED. Each worker locks a batch of rows and skips rows another worker already locked, so workers never wait on each other and never take the same job. NOWAIT is different: instead of skipping, it fails at once if the row is locked, which suits 'someone else is editing this' screens."

BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'PENDING' AND run_at <= now()
ORDER BY run_at
LIMIT 10
FOR UPDATE SKIP LOCKED;          -- worker 1 gets jobs 1-10, worker 2 gets 11-20, nobody blocks
UPDATE jobs SET status = 'RUNNING', locked_by = $worker, locked_at = now() WHERE id = ANY($ids);
COMMIT;                          -- do the actual work outside this short transaction

-- NOWAIT: fail fast
SELECT * FROM loans WHERE id = $1 FOR UPDATE NOWAIT;  -- error 55P03 lock_not_available if busy

Pair it with the partial index ON jobs (run_at) WHERE status = 'PENDING'. Recover jobs stuck in RUNNING after a crash using locked_at plus a timeout. This is how the transactional outbox relay works too.

Database locks vs distributed locks (Redis). When do you need a distributed lock?design

Short answer: "If the data being protected lives in one Postgres database, I use the database: row locks, conditional updates, unique constraints or advisory locks. They're transactional and are released automatically if the process crashes. I use a Redis lock when the work isn't a single database write, like making sure only one pod runs a cron job or calls a rate-limited partner API, and I always give it an expiry."

// Redis lock: SET if Not eXists, with expiry so a crashed holder can't block forever
const token = crypto.randomUUID();
const ok = await redis.set('lock:device-sync:veh42', token, 'PX', 30000, 'NX');
if (!ok) return;                      // someone else holds it
try {
  await syncDevice('veh42');
} finally {
  // release only if we still own it (atomic check-and-delete)
  await redis.eval(
    "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end",
    1, 'lock:device-sync:veh42', token);
}

Pitfalls: if the work takes longer than the TTL, the lock expires and a second worker starts (extend the lock, or use a fencing token that the database checks). Redlock across several Redis nodes is debated for correctness. For money, the final guard should always be the database (constraint, version check or idempotency key), not only a Redis lock.

Tie it to your work: "At TapFin we used Redis locks for device sync and scheduled jobs so only one pod handled a vehicle at a time. BullMQ's own job locks also stop two workers processing the same job."
Scenario: two users try to book the last seat (or withdraw from the same account) at the same moment. How do you make sure only one succeeds?design

Short answer: "Let the database decide in one atomic step. The simplest is a conditional update: UPDATE seats SET booked_by = $user WHERE id = $seat AND booked_by IS NULL. Only one transaction can change the row; the other sees zero rows updated and gets 'sold out'. Back it with a unique constraint so even a bug can't create two bookings."

Options, from simplest:

  1. Atomic conditional update (shown above). One statement, no explicit lock, no deadlock risk.
  2. Unique constraint such as UNIQUE (event_id, seat_no) on bookings. The second insert fails with 23505; map it to 409.
  3. Pessimistic lock when you must read, decide and write several rows: SELECT ... FOR UPDATE, check, update, commit.
  4. Optimistic version check for low-contention cases.
  5. SERIALIZABLE isolation for complex rules across many rows, with retry on 40001.

What not to do: read in the app ("is it free?") and then write in a separate statement without a lock. Between the read and the write, another request can take the seat. That's the classic check-then-act race.

At very high traffic (flash sales), put a Redis counter (DECR) or a queue in front to reject most requests early, and still let the database be the final judge.

Fleet Management System (Fastify, ClickHouse, PostgreSQL)

Why ClickHouse for telemetry and not just PostgreSQL?project
  • Write volume: telemetry is append-only and arrives every few seconds per vehicle. ClickHouse ingests millions of rows per second in batches; Postgres row storage, WAL and indexes get expensive at that rate.
  • Query shape: dashboards scan many rows but few columns ("average SoC per vehicle per day for the last 90 days"). ClickHouse is columnar, so it reads only those columns, compressed. Postgres reads whole rows.
  • Compression: similar values in a column compress 5 to 20 times, so storage and I/O drop sharply.
  • Aggregations: vectorised execution plus materialized views for pre-computed rollups.

Why keep Postgres: ClickHouse is weak at transactions, frequent updates/deletes, point lookups by many keys, and foreign keys. Users, vehicles, loans and alert rules need ACID, so they stay in Postgres. It is the standard OLTP plus OLAP split.

How did you design the ClickHouse table for telemetry?project
CREATE TABLE telemetry
(
  org_id       UInt32,
  vehicle_id   String,
  partner      LowCardinality(String),
  ts           DateTime64(3, 'Asia/Kolkata'),
  soc          Float32,
  status       LowCardinality(String),   -- running / idle / charging / offline
  speed        Float32,
  odometer_km  Float64,
  lat          Float64,
  lng          Float64,
  ingested_at  DateTime DEFAULT now()
)
ENGINE = ReplacingMergeTree(ingested_at)
PARTITION BY toYYYYMM(ts)
ORDER BY (org_id, vehicle_id, ts)
TTL toDateTime(ts) + INTERVAL 18 MONTH;
  • ORDER BY is the sparse primary index. Put the columns you filter on first: tenant, then vehicle, then time. A query for one vehicle's last 7 days reads only a few granules (8,192 rows each by default).
  • PARTITION BY month keeps partitions few and large, and makes dropping old data cheap. Do not partition by day or by vehicle; too many parts hurts merges.
  • ReplacingMergeTree removes duplicates that share the same sorting key when parts merge, so partner retries or re-syncs don't double count. Deduplication is eventual, so queries that must be exact use FINAL or argMax.
  • LowCardinality for enums: dictionary-encoded, much smaller and faster.
  • Daily rollups come from a materialized view into an AggregatingMergeTree or SummingMergeTree table, so dashboards never scan raw rows for 90-day charts.
How do you compute idle time, downtime and driver score?project

Idle time: consecutive points where ignition is on and speed is about 0. Order points per vehicle, compute the gap to the next point with a window function, and sum gaps where the status is idle. Cap each gap (say 5 minutes) so a missing-data hole doesn't count as hours of idling.

SELECT vehicle_id, toDate(ts) AS day,
       sum(if(status = 'idle', least(gap_s, 300), 0)) / 60 AS idle_minutes
FROM (
  SELECT vehicle_id, ts, status,
         dateDiff('second', ts,
           leadInFrame(ts) OVER (PARTITION BY vehicle_id ORDER BY ts
             ROWS BETWEEN CURRENT ROW AND 1 FOLLOWING)) AS gap_s
  FROM telemetry
  WHERE org_id = {org:UInt32} AND ts >= today() - 7
)
GROUP BY vehicle_id, day;

Downtime: intervals where the vehicle is offline (no data beyond a threshold) or flagged under maintenance during operating hours.

Driver score: a weighted formula, for example start at 100 and subtract points for harsh braking or acceleration events per 100 km, overspeeding minutes, and excess idling. Compute daily in a job, store it, and show trends. Be ready to explain the weights you used and why.

Each EV partner sends data in a different format. How did you handle that?project
  • Adapter pattern: one adapter per partner implements fetch() and normalize(raw) → TelemetryEvent. The rest of the pipeline knows only the canonical event.
  • Validation: a Zod schema for the canonical event. Bad records go to a dead-letter topic or table with the reason, so one partner's bad payload never blocks the pipeline.
  • Unit normalisation: SoC as a percentage, timestamps converted to UTC or a single timezone, distances in km, status mapped to our own enum.
  • Adding a partner means writing one new adapter plus config. That's the open/closed principle in practice.
What happens if ClickHouse is down, or a partner sends a burst?project
  • Kafka is the buffer. Ingestion keeps writing to Kafka; the ClickHouse consumer stops committing offsets and resumes from the last committed offset when ClickHouse recovers. Nothing is lost as long as it comes back within the topic's retention period.
  • The writer batches (for example 10k rows or 1 second, whichever comes first). ClickHouse prefers few large inserts; many tiny inserts create too many parts ("Too many parts" error). async_insert is an alternative.
  • Bursts are absorbed by consumer lag. You watch lag and scale consumers up to the number of partitions.
  • Commit offsets only after the insert succeeds, so delivery is at-least-once. Duplicates are handled by ReplacingMergeTree.

How do you avoid processing the same message twice?project

Kafka and BullMQ both give at-least-once delivery in practice, so consumers must be idempotent:

  • Give every event a unique ID. Insert it into a processed_events(event_id PRIMARY KEY) table in the same DB transaction as the side effect; a duplicate hits the unique constraint and is skipped.
  • Or make the write itself idempotent: INSERT ... ON CONFLICT DO NOTHING or an upsert, or ReplacingMergeTree in ClickHouse.
  • BullMQ: pass a jobId derived from the business key. BullMQ ignores adding a job whose ID already exists.
  • For external side effects (send SMS), use a Redis SET NX on the notification ID before sending.

Central auth service (Better Auth, multi-tenant, RBAC)

How did you migrate legacy users without forcing password resets?project

Better Auth hashes with scrypt by default; legacy users had bcrypt hashes. Better Auth lets you supply your own hash and verify functions:

emailAndPassword: {
  enabled: true,
  password: {
    hash: (password) => scryptHash(password),           // new hashes
    verify: async ({ hash, password }) => {
      if (hash.startsWith('$2a$') || hash.startsWith('$2b$')) {
        return bcrypt.compare(password, hash);             // legacy users
      }
      return scryptVerify(hash, password);
    },
  },
}
  • Users were imported with their existing bcrypt hash into the account table.
  • The hash prefix tells you the algorithm ($2b$10$... is bcrypt with cost 10).
  • Optional upgrade: after a successful legacy login, re-hash with the new algorithm and save, so bcrypt hashes disappear over time.
  • Passwords are never decrypted. Hashing is one-way, so this is the only way to migrate without a reset.
How is multi-tenancy and RBAC modelled?project
  • Organisation is the tenant (a fleet operator, a lender, an internal team). A user can belong to several organisations through a member row that holds the role (owner, admin, member, or custom roles).
  • The session stores the active organisation. Every API resolves the session, then checks the member's role for that organisation.
  • Permissions are resource plus action: { loan: ['read','approve'], vehicle: ['read'] }. Roles map to permission sets, checked in a Fastify preHandler hook.

Loan origination system (Prisma)

Explain the loan lifecycle you built.project

Lead → KYC → Credit assessment → QC → Sanction → KFS shared and accepted → Agreement / e-mandate → Finance approval → Invoice → Disbursement (full or partial).

  • Modelled as a state machine: a status column plus a table of allowed transitions and the role allowed to perform each. An API that tries an invalid move (sanction an unverified lead) returns 409 or 422.

What is backpressure, exactly?theory

When a producer is faster than a consumer, data piles up in memory. In Node streams, writable.write() returns false once its internal buffer passes highWaterMark. A well-behaved producer stops and waits for the 'drain' event. pipe() and pipeline() do this automatically; pipeline() also destroys every stream and forwards the error if any stage fails, which plain pipe() does not.

function writeMany(ws, rows) {
  let i = 0;
  (function write() {
    let ok = true;
    while (i < rows.length && ok) ok = ws.write(rows[i++]);
    if (i < rows.length) ws.once('drain', write);
    else ws.end();
  })();
}

NeoBank (personal project)

What is double-entry bookkeeping and how did you enforce it?project

Every money movement is a journal entry with two or more lines whose debits equal credits. A transfer of ₹500 from A to B: debit A ₹500, credit B ₹500. A balance is the sum of an account's lines, so money is never created or destroyed by a bug.

  • A Postgres constraint trigger (deferred to commit) checks that the sum of debits minus credits for each journal is 0, and rejects unbalanced journals.
  • Another trigger rejects UPDATE and DELETE on posted entries. Corrections are made by a reversal entry, so history is never edited.
  • A cached balance column is updated in the same transaction for fast reads, and the reconciliation job checks it against the sum of entries.
How are transfers atomic, concurrency-safe and idempotent?project
async function transfer({ fromId, toId, amount, idemKey, userId }) {
  return withDeadlockRetry(() => db.tx(async (t) => {
    // 1. idempotency: same key returns the stored result
    const prev = await t.oneOrNone(
      'SELECT response FROM idempotency_keys WHERE user_id=$1 AND key=$2', [userId, idemKey]);
    if (prev) return prev.response;

    // 2. lock both accounts in a fixed order to avoid deadlock
    const [a, b] = [fromId, toId].sort();
    await t.any('SELECT id FROM accounts WHERE id IN ($1,$2) ORDER BY id FOR UPDATE', [a, b]);

    // 3. check balance under the lock
    const { balance } = await t.one('SELECT balance FROM accounts WHERE id=$1', [fromId]);
    if (balance < amount) throw new InsufficientFunds();

    // 4. post balanced entries + update balances + outbox event
    const j = await t.one('INSERT INTO journals(kind) VALUES($1) RETURNING id', ['transfer']);
    await t.none(`INSERT INTO entries(journal_id, account_id, debit, credit)
                  VALUES ($1,$2,$3,0), ($1,$4,0,$3)`, [j.id, fromId, amount, toId]);
    await t.none('UPDATE accounts SET balance = balance - $2 WHERE id=$1', [fromId, amount]);
    await t.none('UPDATE accounts SET balance = balance + $2 WHERE id=$1', [toId, amount]);
    await t.none('INSERT INTO outbox(topic, payload) VALUES($1,$2)', ['transfer.completed', { journalId: j.id }]);

    const response = { journalId: j.id, status: 'completed' };
    await t.none('INSERT INTO idempotency_keys(user_id, key, response) VALUES($1,$2,$3)',
                 [userId, idemKey, response]);
    return response;
  }));
}
  • Ordered locks: two transfers A→B and B→A would deadlock if each locked its source first. Locking by ascending ID removes the cycle.
  • Deadlock retry: still retry on Postgres errors 40P01 (deadlock) and 40001 (serialization failure) with small jittered backoff.
  • Idempotency key stored in the same transaction: either the transfer and key both commit, or neither does. A unique index on (user_id, key) handles two concurrent requests with the same key: one waits, then fails on the constraint, then re-reads the stored response. The same key with a different payload should return 422.
  • The test: 50 parallel transfers of ₹100 from an account holding ₹1,000. Exactly 10 succeed, 40 fail with insufficient funds, and the balance ends at 0, never negative.
What is the transactional outbox and why not publish to Kafka directly?project

The dual-write problem: if you commit the DB transaction and then publish to Kafka, a crash in between loses the event. Publish first and then the DB rolls back, and you've announced something that never happened.

Outbox: write the event into an outbox table in the same transaction as the business change. A separate relay reads unpublished rows (SELECT ... FOR UPDATE SKIP LOCKED), publishes to Kafka, and marks them sent. Alternatively use CDC (Debezium reading the WAL). Delivery is at-least-once, so the consumer is idempotent (it records processed event IDs).

How do fraud checks and the suspense account work?project
  • Rules: amount above a threshold, first transfer to a newly added beneficiary (within 24 hours), velocity (more than N transfers in M minutes, counted with Redis INCR plus EXPIRE), daily limit (sum of today's debits).
  • If flagged, money moves from the sender to a suspense account (still double-entry), not to the beneficiary. An admin approves (suspense → beneficiary) or rejects (suspense → sender). Every step is a new balanced journal.
  • Reconciliation: the sum of all account balances must equal 0 for internal accounts, cached balances must equal the sum of entries, and the outbox must have no rows stuck for long.
Why store money as integers?theory

Floating point can't represent most decimals exactly: 0.1 + 0.2 = 0.30000000000000004. Store amounts in the smallest unit (paise) as BIGINT, or use NUMERIC(18,2) in Postgres and a decimal library (decimal.js, big.js) in JS. Note that pg returns NUMERIC and BIGINT as strings by default to avoid precision loss.

JavaScript core concepts

Asked in almost every Node.js round. Answer with a definition, a short example and a practical use.

Explain the JavaScript event loop.theory

JS runs on a single thread with a call stack. Async work (timers, I/O, network) is handed to the environment (browser APIs or libuv in Node). When that work finishes, its callback goes into a queue. The event loop repeats: when the call stack is empty, run all microtasks (promise callbacks, queueMicrotask), then take the next macrotask (timer, I/O callback), run it, drain microtasks again, and so on.

So Promise.then callbacks always run before a setTimeout(fn, 0) queued at the same time. Long synchronous code blocks everything, including timers and incoming requests.

var, let and const. What is the temporal dead zone?theory
  • var: function-scoped, hoisted and initialised to undefined, can be redeclared, creates a property on the global object at top level in scripts.
  • let: block-scoped, hoisted but not initialised, can't be redeclared in the same scope.
  • const: like let, but the binding can't be reassigned. The object it points to can still be mutated (Object.freeze for shallow immutability).

TDZ: from the start of the block until the declaration line, accessing a let/const throws ReferenceError.

What is hoisting?theory

During the creation phase, declarations are registered before code runs. Function declarations are hoisted completely (you can call them before the line). var is hoisted as undefined. let, const and class are hoisted but in the TDZ. Function expressions and arrow functions follow the rules of the variable they're assigned to.

What is a closure? Give a real use.theory

A closure is a function together with the variables from the scope where it was created. It keeps access to them after that outer function returns.

function rateLimiter(limit) {
  let count = 0;                 // private state
  return () => ++count <= limit;
}
const allow = rateLimiter(3);
allow(); allow(); allow(); allow(); // true true true false

Uses: private state (module pattern), function factories, memoization caches, debounce/throttle timers, Express middleware factories like authorize('admin'). Risk: closures keep large objects alive and can cause memory leaks.

How does this work?theory

Decided by how a function is called, not where it is defined (except arrows):

  1. new Foo(): the new object.
  2. fn.call(obj), apply, bind: obj.
  3. obj.fn(): obj.
  4. Plain fn(): undefined in strict mode, the global object otherwise.
  5. Arrow functions have no own this; they use the this of the enclosing scope (lexical). That's why they work inside callbacks but are a poor choice for object methods.
call, apply and bind?theory

All set this. call(ctx, a, b) invokes now with arguments listed. apply(ctx, [a, b]) invokes now with an array. bind(ctx, a) returns a new function with this fixed and optional pre-filled arguments (partial application); it does not invoke.

Prototypes and prototypal inheritance.theory

Every object has an internal link [[Prototype]] (reachable via Object.getPrototypeOf or __proto__). When a property isn't found on the object, JS looks up the chain until null. Functions have a prototype property that becomes the [[Prototype]] of objects created with new. class is syntax over this: methods live on Class.prototype, shared by all instances.

Promises: states, chaining, and the combinators.theory

A promise is pending, then settles once into fulfilled or rejected. .then returns a new promise, so you can chain; throwing inside .then rejects the next one.

async/await: what does it compile to, and common mistakes?theory

An async function always returns a promise. await pauses the function (not the thread) and resumes it as a microtask when the awaited promise settles. It's syntax over promises and generators.

  • Accidental serialisation: for (const id of ids) await fetch(id) runs one by one. Use Promise.all(ids.map(fetch)) with a concurrency limit if there are many.
  • forEach with an async callback doesn't wait. Use for...of or Promise.all.
  • Forgetting await means errors become unhandled rejections and the try/catch doesn't catch them.
  • return await inside try/catch is needed if you want the catch block to handle that rejection.
== versus ===. Type coercion rules worth knowing.theory

=== compares without conversion. == converts types first: null == undefined is true (and neither equals anything else), numbers vs strings convert the string to a number, booleans become numbers, objects become primitives via valueOf/toString. NaN is never equal to anything, itself included (use Number.isNaN). Object.is is like === but Object.is(NaN, NaN) is true and Object.is(0, -0) is false.

Shallow copy versus deep copy.theory

Spread {...obj}, Object.assign and arr.slice() copy only the top level; nested objects are shared. Deep copy: structuredClone(obj) (handles Date, Map, Set and cycles; not functions or class prototypes). JSON.parse(JSON.stringify()) loses Dates (become strings), undefined, functions, Map/Set, and fails on cycles.

Map vs Object, Set vs Array, WeakMap?theory
  • Map: any key type, keeps insertion order, has .size, faster for frequent add/delete, no prototype key collisions. Object: string/symbol keys, good for fixed records and JSON.
  • Set: unique values, O(1) has. Dedupe: [...new Set(arr)].
  • WeakMap: keys must be objects and are held weakly, so the entry disappears when the key is garbage collected. Not iterable. Good for caching metadata about objects without leaking memory.
Debounce versus throttle.theory

Debounce: run only after calls stop for N ms (search box: wait until typing pauses). Throttle: run at most once every N ms (scroll handler, rate-limiting an API). Code is in the coding section.

What are pure functions, currying, higher-order functions?theory

Pure: same input gives the same output and there are no side effects (easy to test). Higher-order: takes or returns a function (map, filter, middleware factories). Currying: f(a, b, c) becomes f(a)(b)(c), useful for partial application.

Optional chaining and nullish coalescing.theory

a?.b?.c returns undefined instead of throwing if a link is null/undefined. x ?? def uses the default only for null/undefined, while x || def also replaces 0, '' and false. Example: limit ?? 20 keeps a legitimate 0.

How does garbage collection work in V8? What causes memory leaks?theory

Mark-and-sweep from roots (global, stack). V8 is generational: a small young generation (scavenged often, most objects die young) and an old generation (mark-sweep-compact, mostly incremental and concurrent). Leaks happen when something reachable keeps references: global caches without limits, event listeners never removed, closures capturing big objects, timers (setInterval) never cleared, unbounded in-memory queues. Node.js internals

The difference between a mid-level and a senior answer is usually here.

How is Node.js single-threaded yet handles thousands of connections?theory

Your JavaScript runs on one thread, but I/O is non-blocking. Network sockets use the operating system's async mechanisms (epoll on Linux, kqueue on macOS, IOCP on Windows) through libuv, so one thread can wait on thousands of sockets. Work that the OS can't do asynchronously (file system, DNS lookup, crypto like pbkdf2/scrypt, zlib) goes to libuv's thread pool (4 threads by default, set with UV_THREADPOOL_SIZE). Node is great for I/O-bound work and poor for CPU-heavy work on the main thread.

Explain the phases of the Node.js event loop.theory
  1. timers: setTimeout / setInterval callbacks whose time has come.
  2. pending callbacks: some system I/O callbacks deferred from the previous loop (for example TCP errors).
  3. idle, prepare: internal.
  4. poll: get new I/O events and run their callbacks; the loop may block here waiting for I/O when nothing else is scheduled.
  5. check: setImmediate callbacks.
  6. close callbacks: for example socket.on('close').

Between every callback, Node drains the process.nextTick queue first and then the promise microtask queue.

process.nextTick vs setImmediate vs setTimeout(0)?theory
  • process.nextTick: runs right after the current operation, before promises and before the loop continues. Recursive nextTick can starve I/O.
  • setImmediate: runs in the check phase of the current or next loop iteration.
  • setTimeout(fn, 0): timers phase, at least 1 ms later.

Prefer setImmediate or queueMicrotask unless you specifically need nextTick (for example emitting an event after a constructor returns).

How do you handle CPU-intensive work in Node?theory
  • worker_threads: real threads in the same process with their own V8 isolate and event loop; communicate via messages or SharedArrayBuffer. Use a pool (Piscina). Good for PDF generation, image processing, heavy parsing, hashing.
  • Offload to a queue: BullMQ workers in a separate process or container.
  • Split the work into chunks with setImmediate between them so the loop can breathe.
  • Use a different language or service for heavy compute.

Detect blocking with event loop lag (perf_hooks.monitorEventLoopDelay) or clinic.js.

Streams: types and why use them.theory

Four types: Readable (fs.createReadStream, HTTP request), Writable (HTTP response, file write), Duplex (TCP socket), Transform (zlib gzip, CSV parser). They process data in chunks, so memory stays constant regardless of size, and processing starts before all data has arrived. Object mode streams pass JS objects instead of bytes. Always use pipeline() for error handling and cleanup. See the export engine answer for backpressure.

What is a Buffer?theory

A fixed-size chunk of raw binary memory outside the V8 heap (a Uint8Array subclass). Used for files, sockets, crypto. Buffer.from('hi', 'utf8'), buf.toString('base64'). Beware: slicing a buffer shares memory, and Buffer.allocUnsafe may contain old data.

EventEmitter: how does it work, any gotchas?theory

on registers listeners, emit calls them synchronously in order, once auto-removes. Gotchas: an 'error' event with no listener throws and crashes the process; more than 10 listeners logs a possible memory leak warning; forgetting removeListener leaks.

How do you handle errors properly in Node?theory
  • Operational errors (DB down, timeout, invalid input) are expected: handle them, retry, return a proper HTTP status. Programmer errors (undefined is not a function) are bugs: log and let the process restart.
  • Async/await with try/catch, plus a central error handler in the framework (Express 4 error middleware with 4 args, Fastify setErrorHandler).
  • Custom error classes with a code and HTTP status (NotFoundError, ValidationError).
  • process.on('unhandledRejection') and 'uncaughtException': log, then exit and let the orchestrator restart, because the state may be corrupt.
  • Never leak stack traces to clients in production.

How would you find why a Node API is slow?theory
  1. Measure: p50/p95/p99 latency per route, from APM or logs with timing (Fastify logs response time).
  2. Is it the DB? Log slow queries, run EXPLAIN ANALYZE, look for missing indexes, N+1 queries, and connection pool waits.
  3. External calls? Add timeouts and measure each one; parallelise independent calls.
  4. Event loop blocked? Check event loop lag; profile with --cpu-prof or clinic flame graphs (big JSON.stringify, sync crypto, regex backtracking, huge loops).
  5. Memory or GC pressure? Heap growth, long GC pauses.
  6. Fix with caching (Redis), pagination, indexes, moving work to background jobs, streaming responses.
What does require do? Module caching?theory

Resolves the path (core module, relative file, then node_modules up the tree), wraps the file in a function (exports, require, module, __filename, __dirname), runs it once, and caches module.exports in require.cache. Later requires return the same object, which is why a module works as a singleton (for example one DB pool). Circular requires get a partially filled exports object.

How do you secure environment variables and config?theory

Never commit secrets (.env in .gitignore, secret scanning in CI). Load from a secrets manager (AWS Secrets Manager, SSM Parameter Store, Vault) or orchestrator secrets. Validate config at startup with Zod and fail fast if something is missing. Different values per environment. Rotate keys.

Fastify, Express, NestJS and API design

Why Fastify over Express?theory
  • Speed: much higher throughput, largely from schema-based serialisation (fast-json-stringify compiles a serialiser from the response JSON schema) and an efficient router (find-my-way, radix tree).
  • Schema-first: request validation with JSON Schema (Ajv) built in, and the same schemas generate Swagger docs. Response schemas also strip fields you didn't declare, so you don't leak data by accident.
  • Encapsulated plugins: fastify.register() creates a scope; decorators and hooks registered inside don't leak out unless wrapped with fastify-plugin.
  • Lifecycle hooks: onRequest → preParsing → preValidation → preHandler → handler → preSerialization → onSend → onResponse, plus onError.
  • Built-in Pino logger with request IDs, and native async/await support (a thrown error in an async handler becomes a proper error response). Express 4 needed wrappers for that; Express 5 now handles rejected promises.
How does Express middleware work?theory

An ordered chain of functions (req, res, next). Each either ends the response or calls next(). next(err) skips to error middleware, which has four parameters (err, req, res, next) and must be registered last. Order matters: body parser before routes, auth before protected routes.

const authorize = (...roles) => (req, res, next) =>
  roles.includes(req.user?.role) ? next() : res.status(403).json({ error: 'Forbidden' });

app.use((err, req, res, next) => {
  req.log?.error(err);
  res.status(err.status ?? 500).json({ error: err.expose ? err.message : 'Internal error' });
});
NestJS basics: modules, providers, DI, guards, interceptors, pipes.theory
  • Module: groups controllers and providers. Controller: routes. Provider (service): business logic, injected by the DI container through constructor parameters.
  • Request pipeline: Middleware → Guards (authorisation, return true/false) → Interceptors (before/after: logging, caching, transforming responses) → Pipes (validate and transform input, for example ValidationPipe with class-validator) → Handler → Interceptors after → Exception filters.
  • It can run on Express or Fastify underneath.
REST API design best practices.theory
  • Nouns for resources, HTTP verbs for actions: GET /loans/:id, POST /loans/:id/sanction for state transitions that aren't plain updates.
  • Correct status codes: 200, 201 Created, 204 No Content, 400 bad input, 401 not authenticated, 403 not allowed, 404, 409 conflict (wrong state, duplicate), 422 validation, 429 rate limited, 500, 503.
  • Pagination (cursor-based for large or changing data, offset for small admin lists), filtering, sorting.
  • Versioning (/v1 or header), consistent error format ({ code, message, details }), idempotency keys for POSTs that move money, OpenAPI docs.
PUT vs PATCH. Which methods are idempotent?theory

PUT replaces the whole resource; PATCH updates part of it. Idempotent (same result if repeated): GET, PUT, DELETE, HEAD, OPTIONS. Not idempotent: POST, and PATCH in general (for example "increment by 1"). Safe (no side effects): GET, HEAD, OPTIONS.

Offset vs cursor pagination.theory

LIMIT 20 OFFSET 100000 makes the DB read and discard 100,000 rows, and rows shift if data is inserted meanwhile. Cursor (keyset) pagination: WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20, using an index. It's constant speed and stable, but you can't jump to page N.

REST vs GraphQL vs gRPC vs WebSocket.theory
  • REST: simple, cacheable, the default for public and CRUD APIs.
  • GraphQL: the client asks for exactly the fields it needs in one round trip; good for many clients with different needs. Downsides: N+1 in resolvers (use DataLoader), harder HTTP caching, query cost limits needed.
  • gRPC: binary Protobuf over HTTP/2, typed contracts, streaming; good for internal service-to-service calls.
  • WebSocket: persistent two-way connection for real-time updates (live vehicle positions, notifications). Server-Sent Events if only the server pushes.
Zod: why validate at runtime when you have TypeScript?theory

TypeScript types disappear at compile time; data from requests, partner APIs, env vars or queues can be anything. Zod checks it at runtime and infers the TS type from the same schema (z.infer<typeof Schema>), so validation and types never drift apart. safeParse returns errors instead of throwing.

What is CORS?theory

A browser rule: a page from origin A can't read responses from origin B unless B allows it with Access-Control-Allow-Origin. Non-simple requests (custom headers, PUT/DELETE, JSON content type) send a preflight OPTIONS first. With cookies you need Allow-Credentials: true and a specific origin, not *. CORS protects users in browsers; it is not server-side security (curl ignores it).

PostgreSQL and database theory

ACID properties.theory

Atomicity: all or nothing (transfer debit and credit together). Consistency: constraints always hold. Isolation: concurrent transactions don't see each other's partial work (to the level chosen). Durability: once committed, it survives a crash (write-ahead log flushed to disk).

What is MVCC?theory

Multi-Version Concurrency Control. An UPDATE writes a new row version instead of overwriting; each row version carries the creating and deleting transaction IDs (xmin/xmax). Each transaction sees a snapshot, so readers never block writers and writers never block readers. Old versions become dead tuples, cleaned by VACUUM (autovacuum). Heavy update tables bloat if vacuum can't keep up.

Index types and when to use them.theory
  • B-tree (default): equality, range, sorting, prefix LIKE 'abc%'.
  • Hash: equality only.
  • GIN: many values per row: JSONB containment (@>), arrays, full-text search, trigram for ILIKE '%x%' (pg_trgm).
  • GiST: geometry, ranges, nearest-neighbour (PostGIS).
  • BRIN: tiny index for huge tables naturally ordered by a column, like append-only time series.
  • Partial: CREATE INDEX ON loans(status) WHERE status = 'PENDING'. Expression: ON users (lower(email)). Covering: INCLUDE (amount) for index-only scans.

Composite index (org_id, status, created_at) helps queries that filter on the leftmost columns. A query on status alone can't use it efficiently.

When does an index not get used?theory

A function on the column (WHERE lower(email) = ... without an expression index), leading wildcard LIKE '%x', type mismatch or implicit casts, low selectivity (the planner prefers a sequential scan when it would read most of the table), stale statistics (run ANALYZE), OR across different columns, skipping the leading column of a composite index.

How do you read EXPLAIN ANALYZE?theory

Read the plan tree from the inside out. Look for Seq Scan on big tables with a selective filter (missing index), a big gap between estimated and actual rows (stale stats), Nested Loop over many rows, sorts spilling to disk (Sort Method: external merge, raise work_mem or add an index), and Rows Removed by Filter being large. Use EXPLAIN (ANALYZE, BUFFERS) to see I/O.

Row locks: FOR UPDATE, FOR SHARE, SKIP LOCKED, NOWAIT.theory
  • FOR UPDATE: lock the selected rows until commit; others wanting to update or lock them wait.
  • FOR SHARE: others can read-lock too but not update.
  • SKIP LOCKED: skip rows locked by others. Perfect for job queues and outbox relays where several workers pick different rows.
  • NOWAIT: error at once instead of waiting.
What is a deadlock and how do you prevent it?theory

T1 locks row A and waits for B; T2 locks B and waits for A. Postgres detects the cycle (after deadlock_timeout, 1 s by default) and aborts one with error 40P01. Prevent: lock rows in a consistent order (sorted IDs), keep transactions short, don't call external services inside a transaction, and retry the aborted transaction.

Normalisation: 1NF, 2NF, 3NF. When do you denormalise?theory

1NF: atomic values, no repeating groups. 2NF: no attribute depends on only part of a composite key. 3NF: no attribute depends on another non-key attribute (no transitive dependency). Denormalise for read performance: a cached balance, a precomputed daily summary, a copied customer name on an invoice (which also preserves history). Keep the source of truth and a way to reconcile.

JOIN types.theory

INNER (matches only), LEFT (all left rows, nulls where no match), RIGHT, FULL OUTER, CROSS (every combination), SELF join (employee and manager in the same table). Anti-join: LEFT JOIN ... WHERE right.id IS NULL or NOT EXISTS. Avoid NOT IN when the subquery can return NULL (it then returns nothing).

WHERE vs HAVING; order of SQL execution.theory

Logical order: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. WHERE filters rows before grouping; HAVING filters groups after aggregation. That's why you can't use a SELECT alias in WHERE.

Partitioning, replication, sharding, connection pooling.theory
  • Partitioning: one logical table split by range (month), list (region) or hash. Queries prune irrelevant partitions; old data is dropped cheaply.
  • Replication: streaming replicas for read scaling and failover. Replicas lag slightly, so read-your-own-writes needs the primary.
  • Sharding: data split across separate servers by a key (org_id). Hard: cross-shard queries and transactions. Citus is a Postgres option.
  • Pooling: each Postgres connection is a process (several MB). PgBouncer in transaction mode lets thousands of clients share a few connections. App-level pool size times instances must stay under max_connections.
Triggers, views, materialized views, stored procedures.theory

Trigger: function run on INSERT/UPDATE/DELETE (NeoBank uses them to reject unbalanced or edited journals). View: a saved query. Materialized view: stored result refreshed with REFRESH MATERIALIZED VIEW CONCURRENTLY (needs a unique index). Procedure/function: logic in the DB, which is fast and atomic but harder to version, test and debug, so use it sparingly.

How do you run a migration on a big table without downtime?theory
  • Add a nullable column (instant). Adding a column with a constant default is also instant since Postgres 11.
  • CREATE INDEX CONCURRENTLY to avoid locking writes.
  • Backfill in batches, not one giant UPDATE.
  • Expand and contract: add the new column, write to both, backfill, switch reads, then drop the old column in a later release.
  • Set lock_timeout so a migration waiting for a lock doesn't queue up all traffic behind it.

ClickHouse

How does ClickHouse store data? What is MergeTree?theory
  • Columnar: each column is stored in its own compressed file, sorted by the table's ORDER BY key.
  • Each INSERT writes an immutable part; background processes merge parts into bigger ones (like an LSM tree). That's why many tiny inserts are bad.
  • Sparse primary index: one index entry per granule (8,192 rows by default), not per row. Lookups find candidate granules, then scan them. Small enough to stay in memory.
  • The primary key doesn't enforce uniqueness.
MergeTree family: Replacing, Summing, Aggregating, Collapsing.theory
  • ReplacingMergeTree(ver): keeps the latest version per sorting key when merging. Use for deduplication or "latest state". Not immediate: use FINAL or argMax(col, ver) to get exact results.
  • SummingMergeTree: sums numeric columns for rows with the same key on merge.
  • AggregatingMergeTree: stores aggregate states (avgState, uniqState) that you finish with avgMerge. Used with materialized views for rollups.
  • CollapsingMergeTree / VersionedCollapsing: cancel rows using a sign column (+1/-1) for updates.

A ClickHouse MV is an insert trigger: when a block is inserted into the source table, the MV's SELECT runs on that block only and writes the result to a target table. It doesn't recompute from scratch, and it doesn't see rows inserted before it was created (you backfill manually).

Why are updates and deletes hard in ClickHouse?theory

Parts are immutable. ALTER TABLE ... UPDATE/DELETE are mutations that rewrite whole parts in the background: heavy and asynchronous. Lightweight DELETE FROM marks rows hidden and cleans up on merge. Design around it: append new versions (ReplacingMergeTree), use TTL for expiry, and drop whole partitions.

Redis

Why is Redis fast? Is it single-threaded?theory

In memory, efficient data structures, and commands run on a single thread, so there are no locks and each command is atomic. Since Redis 6, network I/O can use extra threads, but command execution is still single-threaded. A slow command (KEYS *, a huge SMEMBERS) blocks everyone; use SCAN.

Data types and what you used them for.theory
  • String: cache values, counters (INCR), locks (SET NX PX).
  • Hash: an object (latest vehicle state fields).
  • List: simple queues. Set: unique members (online vehicles). Sorted set: leaderboards (driver scores), sliding-window rate limiting, delayed jobs (BullMQ uses these).
  • Stream: append-only log with consumer groups. Pub/Sub: fire-and-forget broadcast (no persistence). Also Geo, HyperLogLog, Bitmap.
Caching patterns and invalidation.theory
  • Cache-aside (most common): read cache; on miss read DB and set cache with TTL; on write update the DB then delete the cache key.
  • Write-through: write cache and DB together. Write-behind: write cache, flush to DB later (risk of loss).
  • Always set a TTL. Add random jitter to TTLs to avoid many keys expiring together.
  • Cache stampede: many requests miss at once and hammer the DB. Fix with a lock so only one request rebuilds (SET lock NX), or serve stale while refreshing.
  • Penetration (requests for keys that don't exist): cache the empty result briefly.
Eviction policies and persistence.theory

When maxmemory is reached: noeviction (writes fail; required for BullMQ so jobs never vanish), allkeys-lru, volatile-lru (only keys with TTL), allkeys-lfu, volatile-ttl, random. Persistence: RDB snapshots (compact, may lose minutes), AOF append log (fsync every second, loses at most about 1 s), or both.

Implement a distributed lock with Redis.coding
const { randomUUID } = require('node:crypto');

async function withLock(redis, key, ttlMs, fn) {
  const token = randomUUID();
  const ok = await redis.set(`lock:${key}`, token, 'PX', ttlMs, 'NX');
  if (!ok) throw new Error('locked');
  try { return await fn(); }
  finally {
    // delete only if we still own it (atomic check-and-delete)
    await redis.eval(
      `if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`,
      1, `lock:${key}`, token);
  }
}

The token prevents deleting a lock someone else acquired after yours expired. If work can exceed the TTL, extend the lock periodically or use fencing tokens. For correctness-critical locks prefer a DB row lock.

Rate limiter with Redis (fixed window and sliding window).coding
// fixed window: simple, allows bursts at window edges
async function fixedWindow(redis, id, limit, windowSec) {
  const key = `rl:${id}:${Math.floor(Date.now() / 1000 / windowSec)}`;
  const n = await redis.incr(key);
  if (n === 1) await redis.expire(key, windowSec);
  return n <= limit;
}

// sliding window log with a sorted set
async function slidingWindow(redis, id, limit, windowMs) {
  const key = `rl:${id}`, now = Date.now();
  const res = await redis.multi()
    .zremrangebyscore(key, 0, now - windowMs)
    .zadd(key, now, `${now}-${Math.random()}`)
    .zcard(key)
    .pexpire(key, windowMs)
    .exec();
  return res[2][1] <= limit;
}

For strict correctness under concurrency, put the sliding-window logic in one Lua script so it's atomic.

Kafka and BullMQ

Kafka core concepts: topic, partition, offset, broker, consumer group.theory
  • Topic: named stream of records. Split into partitions, each an ordered, append-only log stored on brokers and replicated (replication factor, usually 3).
  • Offset: a record's position in a partition. Consumers track which offset they've processed.
  • Producer chooses the partition by hashing the message key, so all events for one vehicle go to the same partition and stay in order.
  • Consumer group: each partition is assigned to exactly one consumer in the group. Parallelism equals the number of partitions; extra consumers sit idle. Different groups each get all messages.
  • Records are retained by time or size whether or not they were consumed, so you can replay by resetting offsets.
  • Cluster metadata: ZooKeeper in older versions, KRaft in newer ones (ZooKeeper removed in Kafka 4.0).
Delivery semantics: at-most-once, at-least-once, exactly-once.theory
  • At-most-once: commit the offset before processing. A crash loses the message.
  • At-least-once: process, then commit. A crash after processing but before committing causes a redelivery, so make the consumer idempotent. This is what most systems use.
  • Exactly-once: idempotent producer (enable.idempotence, dedupe by producer ID and sequence) plus transactions, which make consume-transform-produce within Kafka atomic. Once you write to an external DB, you're back to at-least-once plus idempotency, or you store offsets in the same DB transaction as the result.
How is ordering guaranteed? What breaks it?theory

Only within a partition. Use a key (vehicleId, loanId) so related events share a partition. Breaks when: you change the partition count (the key-to-partition mapping changes), producer retries without idempotence with several in-flight requests, or the consumer processes messages from one partition in parallel.

What is consumer rebalancing? Problems?theory

When a consumer joins, leaves or misses heartbeats (or takes longer than max.poll.interval.ms between polls), the group reassigns partitions. During an eager rebalance consumption pauses. A slow handler that exceeds the poll interval causes repeated rebalances and duplicate processing. Fixes: keep handlers fast, process in batches, cooperative-sticky assignment, static membership, and commit before partitions are revoked.

How do you handle a poison message?theory

A message that always fails blocks its partition forever if you keep retrying. Retry a few times with backoff (or via retry topics with delays), then publish it to a dead-letter topic with the error and original metadata, commit the offset and move on. Alert on DLQ volume and offer a replay tool.

Consumer lag: what is it and how do you fix it?theory

Lag is the latest offset minus the committed offset per partition: how far behind consumers are. Fixes: add consumers (up to the partition count), add partitions (plan for ordering impact), batch processing (eachBatch in kafkajs, batched DB inserts), make handlers faster, and move slow side effects to a queue.

Kafka vs RabbitMQ vs SQS.theory

How does BullMQ work internally?theory
  • Jobs are hashes in Redis; queue states are lists and sorted sets: wait, active, delayed (sorted by run time), prioritized, completed, failed.

  • A worker moves a job from wait to active and holds a lock it renews. If the worker dies, the lock expires and the job is detected as stalled and moved back to wait.
  • Features: concurrency per worker, global rate limiter, repeatable jobs and job schedulers (cron), FlowProducer (parent and child jobs), events via QueueEvents, deduplication by jobId.
  • Redis must use maxmemory-policy noeviction.

Authentication and security

Authentication vs authorisation.theory

Authentication: who are you (login, OTP, token). Authorisation: what may you do (RBAC check). 401 means not authenticated; 403 means authenticated but not allowed.

How does a JWT work? Can it be revoked?theory

header.payload.signature, each base64url-encoded. The payload is readable by anyone, only signed, so never put secrets in it. HS256 uses one shared secret; RS256/ES256 use a private key to sign and a public key (JWKS) to verify, so other services can verify without the secret. Verify the signature, exp, iss, aud, and pin the algorithm (reject alg: none).

Revocation: JWTs are valid until expiry, so keep access tokens short (5 to 15 minutes), use refresh tokens stored server-side that you can revoke, and optionally keep a denylist of token IDs (jti) in Redis.

Access token and refresh token flow; where to store tokens.theory
  • Short access token for API calls; long refresh token to get new access tokens.
  • Refresh token rotation: each refresh issues a new refresh token and invalidates the old. If an old one is used again, treat it as theft and revoke the whole token family.
  • Browser storage: refresh token in an HttpOnly; Secure; SameSite cookie (JS can't read it, so XSS can't steal it). Access token in memory. localStorage is readable by any injected script.
  • Mobile: secure storage (Keychain, Keystore).
OAuth 2.0 flows and PKCE.theory
  • Authorization Code + PKCE: for web and mobile apps. The user logs in at the provider, the app gets a code, then exchanges it for tokens. PKCE: the app sends a hash of a random secret (code_challenge) at the start and the secret itself (code_verifier) at exchange, so a stolen code is useless.
  • Client Credentials: machine to machine, no user.
  • Refresh Token grant.
  • Implicit and password grants are deprecated.
  • OAuth is authorisation (delegated access). OpenID Connect adds authentication on top (ID token, userinfo endpoint).
Why bcrypt instead of SHA-256 for passwords?theory

SHA-256 is designed to be fast, so attackers can try billions of guesses per second on GPUs. bcrypt, scrypt and Argon2 are deliberately slow and tunable (cost factor), and scrypt/Argon2 are also memory-hard. Each hash includes a random salt, so identical passwords produce different hashes and rainbow tables don't work. bcrypt cost 10 to 12 is typical; bcrypt only uses the first 72 bytes of the password. In Node, bcrypt runs on the libuv thread pool, so many concurrent logins can saturate those 4 threads.

RBAC vs ABAC.theory

RBAC: permissions attached to roles, roles to users. Simple and auditable. ABAC: decisions based on attributes of user, resource and context ("a credit officer can approve loans under ₹5 lakh in their own branch during working hours"). Real systems mix them: RBAC for coarse access, attribute checks (ownership, tenant, amount limit) in code.

OWASP Top 10 issues and how you prevent them in Node.theory
  • Broken access control (most common): check ownership and tenant on every request, not just "is logged in". IDOR: GET /loans/123 must verify loan 123 belongs to the caller's org.
  • Injection: parameterised queries and ORMs; never concatenate input into SQL or shell commands. NoSQL injection: reject objects where strings are expected ({"$ne": null}), which schema validation handles.
  • Cryptographic failures: TLS everywhere, encrypt PII at rest (PAN, Aadhaar reference), strong hashing.
  • Security misconfiguration: Helmet headers, disable stack traces, least-privilege IAM, no default credentials.
  • Vulnerable dependencies: npm audit, Dependabot, SonarQube, lockfiles.
  • Authentication failures: rate limiting, lockout, MFA, secure session cookies.
  • SSRF: don't fetch arbitrary user-supplied URLs; allowlist hosts.
  • Logging failures: log security events, and never log passwords, tokens, OTPs or full PAN/Aadhaar.
XSS and CSRF: what they are and how to stop them.theory

XSS: an attacker's script runs in your page (stored or reflected input rendered as HTML). Prevent: escape output (React does by default; avoid dangerouslySetInnerHTML), Content-Security-Policy, HttpOnly cookies.

CSRF: another site makes the user's browser send an authenticated request using their cookies. Prevent: SameSite=Lax/Strict cookies, CSRF tokens, checking the Origin header. APIs authenticated by an Authorization header (not cookies) aren't vulnerable.

How do you protect PII like PAN and Aadhaar?theory

Collect only what's needed. Store Aadhaar masked (only the last 4 digits) plus the provider reference. Encrypt sensitive fields at the application level (AES-256-GCM with keys from KMS), mask in logs and API responses, restrict access by role and audit every view, apply retention limits, and follow the DPDP Act 2023 and RBI data localisation rules (payment data stored in India).

AWS

Lambda: how it works, cold starts, limits.theory
  • Event-driven functions; AWS runs a container (execution environment) per concurrent request and reuses it for later invocations.
  • Cold start: a new environment must start, load code and run init. Reduce it with a smaller bundle (esbuild, tree-shaking), fewer dependencies, more memory (more CPU), provisioned concurrency, and initialising clients outside the handler so warm calls reuse them.
  • Limits: 15 minutes max run time, up to 10 GB memory, 6 MB synchronous payload, default 1,000 concurrent executions per region (a soft limit).
  • DB connections: many concurrent Lambdas can exhaust Postgres connections. Use RDS Proxy or keep one connection per container.
API Gateway: REST vs HTTP API, and what it gives you.theory

Managed front door: routing to Lambda or HTTP backends, authorisers (Cognito, JWT, Lambda authoriser), throttling, usage plans and API keys, request validation, CORS, stages. HTTP APIs are cheaper and faster with fewer features; REST APIs have more (request transformation, WAF, caching, usage plans). The default integration timeout is 29 seconds, so long work must be async.

S3: storage classes, presigned URLs, consistency.theory
  • Object storage, 11 nines durability. Classes: Standard, Intelligent-Tiering, Standard-IA, Glacier. Lifecycle rules move or delete old objects.
  • Presigned URL: a time-limited signed URL that lets a client upload or download a specific object directly, without your server handling the bytes or having public buckets. Used for exports and KYC document uploads.
  • Strong read-after-write consistency since December 2020.
  • Multipart upload for large files (required over 5 GB). Versioning to keep earlier versions (CSR documents). Block public access by default.
SNS vs SQS vs EventBridge.theory

SNS: pub/sub push to many subscribers (SQS, Lambda, HTTP, SMS, email). SQS: a queue consumers pull from, with visibility timeout, retries and DLQ. Fan-out pattern: SNS topic to several SQS queues, so each service processes at its own pace. EventBridge: event bus with content-based routing rules, schedules and SaaS integrations.

Cognito: user pools vs identity pools.theory

User pool: user directory and authentication; issues JWTs (ID, access, refresh); supports MFA, social login, hosted UI, Lambda triggers. Identity pool: exchanges a login (from a user pool, Google, etc.) for temporary AWS credentials so clients can call AWS services directly, such as uploading to S3.

Step Functions: when to use them.theory

Orchestrate multi-step workflows as a state machine (JSON/ASL): sequence, choice, parallel, map, wait, retry with backoff and catch per step, human approval via task tokens. Standard: up to one year, exactly-once per step, auditable history, priced per state transition. Express: up to 5 minutes, high volume, at-least-once, cheaper. Good for document pipelines and approval flows like the CSR workflow.

EC2 vs Lambda vs ECS/Fargate.theory

Lambda: spiky or event-driven, short tasks, pay per use, no servers. ECS/Fargate: containers without managing servers; long-running services, WebSockets, Kafka consumers. EC2: full control, steady load, cheapest at constant use (reserved or savings plans). A Kafka consumer or a ClickHouse writer belongs on containers, not Lambda.

IAM basics.theory

Users, groups, roles, policies (JSON with Effect, Action, Resource, Condition). Grant least privilege. Services (Lambda, ECS tasks) assume roles and get temporary credentials; never put access keys in code. An explicit Deny always wins.

MinIO: what and why?theory

Self-hosted S3-compatible object storage. The same AWS SDK code works against it by changing the endpoint (and setting forcePathStyle: true). Useful for on-prem, local development, or to avoid cloud lock-in and egress cost.

Docker, Jenkins and CI/CD

Container vs virtual machine.theory

A VM virtualises hardware and runs a full guest OS. A container shares the host kernel and isolates processes with namespaces (what it can see) and cgroups (how much CPU and memory it can use). Containers start in seconds and are much smaller; VMs give stronger isolation.

Image vs container; layers and caching; reducing image size.theory

An image is a read-only template made of layers (one per instruction); a container is a running instance with a thin writable layer. Docker reuses cached layers until an instruction or its inputs change, and every later layer then rebuilds. So put rarely-changing steps first (copy package files and install before copying source). Reduce size: multi-stage builds, alpine or distroless base images, .dockerignore (node_modules, .git, tests), npm ci --omit=dev, and clean up in the same RUN instruction.

CMD vs ENTRYPOINT; COPY vs ADD.theory

ENTRYPOINT is the fixed executable; CMD gives default arguments that docker run can override. Use the exec (JSON array) form so your process is PID 1 and receives signals. COPY just copies; ADD also extracts tar files and fetches URLs. Prefer COPY.

docker-compose: what for?theory

Define multi-container apps in YAML: the API, Postgres, Redis, Kafka, ClickHouse, with networks, volumes, env vars and health checks. Good for local development and integration tests. Note that depends_on only waits for health if you use condition: service_healthy.

CI vs continuous delivery vs continuous deployment; deployment strategies.theory

CI: every merge builds and tests automatically. Continuous delivery: every passing build can be released with a button. Continuous deployment: it ships to production automatically. Strategies: rolling (replace instances gradually), blue-green (switch traffic between two full environments, instant rollback), canary (send a small percentage to the new version first), feature flags (deploy dark, enable later).

What does SonarQube check?theory

Static analysis: bugs, code smells, vulnerabilities and security hotspots, duplicated code, complexity, test coverage. A quality gate (for example coverage on new code above 80%, no new critical issues) can fail the build.

Logging and monitoring: what do you set up?theory
  • Structured JSON logs (Pino) with a request or correlation ID passed across services, log levels, no PII.
  • Metrics: request rate, error rate, latency percentiles (RED), plus queue depth, Kafka lag, DB pool usage, event loop lag. Prometheus and Grafana, or CloudWatch.
  • Tracing: OpenTelemetry to follow one request through services.
  • Alerts on symptoms users feel (error rate, p95 latency, lag growing), not on every CPU spike.

CAP theorem and PACELC.theory

During a network Partition, a distributed system must choose Consistency (refuse or error rather than return stale data) or Availability (answer, possibly stale). Partitions will happen, so the real choice is C or A when they do. PACELC adds: Else (no partition), choose Latency or Consistency. Payments and ledgers choose consistency; feeds, dashboards and caches choose availability.

How do you make an API idempotent?theory

The client sends an Idempotency-Key header (a UUID per logical operation). The server stores the key with a hash of the request and the response, in the same transaction as the operation, under a unique constraint. Repeat with the same key: return the stored response. Same key with a different body: 422. A request still in progress with that key: 409. Expire keys after 24 hours or more. Also use natural keys (unique on payment reference) and conditional updates.

Microservices and architecture patterns

Monolith vs microservices: trade-offs.theory

Microservices: independent deploys and scaling, team ownership, fault isolation, technology freedom. Costs: network calls fail, distributed transactions, data consistency, operational overhead (CI, monitoring, tracing per service), harder debugging. Monolith (or modular monolith) is better for small teams and early products. Split along business boundaries (bounded contexts), not technical layers.

Synchronous vs asynchronous communication between services.theory

Sync (REST, gRPC): simple, immediate answer, but creates temporal coupling. If B is down, A fails, and latencies add up along a chain. Async (events through Kafka, queues): decoupled and resilient, absorbs spikes, but eventually consistent and harder to trace. Use sync for queries that need an answer now, async for "something happened" and side effects.

Saga pattern: choreography vs orchestration.theory

A business transaction across services as a series of local transactions, each with a compensating action if a later step fails (refund, release stock, reverse entry). Choreography: each service reacts to events; no central coordinator; simple for 2 to 3 steps, hard to follow beyond. Orchestration: a central orchestrator (Step Functions, Temporal, a workflow service) tells each service what to do and tracks state; easier to reason about and monitor. Two-phase commit is avoided because it blocks and couples services.

Circuit breaker.theory

Wraps calls to a dependency. Closed: calls pass, failures counted. Past a threshold it goes Open: calls fail immediately (or use a fallback) without hitting the struggling service. After a cooldown, Half-open: let a few test calls through; success closes it, failure reopens. Library: opossum in Node. It stops cascading failures and threads piling up waiting on timeouts.

API gateway pattern.theory

A single entry point for clients: routing, authentication, rate limiting, TLS, request aggregation, CORS, logging. Keeps those concerns out of each service. Backend-for-frontend (BFF) is a variation with one gateway per client type (web, mobile).

Database per service. How do you query across services?theory

Each service owns its data; others go through its API or events, never its tables. For cross-service views: API composition (call several services and join in memory), or CQRS read models built by consuming events into a query-optimised store (for example a lender dashboard store fed by loan and telemetry events).

CQRS and event sourcing.theory

CQRS: separate write models (validate commands, enforce rules) from read models (denormalised for queries). Your Postgres-for-writes plus ClickHouse-for-dashboards setup is a form of it. Event sourcing: store the sequence of events as the source of truth and derive current state by replaying them. A double-entry ledger is close to this: balances are derived from immutable entries. Benefits: full audit, time travel. Costs: complexity, schema evolution of events, snapshots for performance.

Service discovery and configuration.theory

Services find each other through DNS in Kubernetes or ECS service discovery, or a registry like Consul. Configuration through environment variables and a config or secrets store, validated at startup.

class LRUCache {

  get(key) {
    if (!this.map.has(key)) return -1;

    this.map.delete(key); this.map.set(key, v);   // move to most-recent end

Virtual DOM and reconciliation.theory

Rendering produces a tree of elements (plain objects). On state change React renders a new tree, diffs it against the previous one, and applies the minimal DOM changes. Heuristics: a different element type replaces the subtree; lists are matched by key. The Fiber architecture lets React split rendering into interruptible units and prioritise urgent updates.

Why do keys matter? Why not use the index?theory

Keys tell React which item is which between renders. With index keys, inserting or deleting at the top shifts every key, so React reuses the wrong component instances: input values and state appear on the wrong rows, and performance suffers. Use a stable ID.

useEffect: dependencies, cleanup, common bugs.theory

Runs after render. Dependencies control when it re-runs (empty array means after mount only). useMemo vs useCallback vs React.memo.theory

useMemo caches a computed value; useCallback caches a function reference; React.memo skips re-rendering a component if its props are shallow-equal. They work together: memoised children need stable callback props. Use them for measured problems, not everywhere.

State management: when local state, Context, Redux/Zustand, React Query?theory

Local state first; lift it up when siblings need it. Context for rarely changing global values (theme, current user), since every consumer re-renders on change. Server data (lists, details) belongs in TanStack Query or SWR, which handle caching, refetching and loading states. Redux Toolkit or Zustand for complex client state shared widely.

Controlled vs uncontrolled components.theory

Controlled: the input value lives in React state and changes through onChange. Uncontrolled: the DOM holds the value and you read it via a ref. Form libraries like React Hook Form use uncontrolled inputs for performance.

function useDebounce(value, ms = 400) {
  const [v, setV] = useState(value);
  useEffect(() => { const t = setTimeout(() => setV(value), ms); return () => clearTimeout(t); }, [value, ms]);
  return v;
}

function useFetch(url) {
  const [state, setState] = useState({ data: null, error: null, loading: true });
  useEffect(() => {
    const ctrl = new AbortController();
    setState(s => ({ ...s, loading: true }));
    fetch(url, { signal: ctrl.signal })
      .then(r => r.ok ? r.json() : Promise.reject(new Error(r.statusText)))
      .then(data => setState({ data, error: null, loading: false }))
      .catch(error => { if (error.name !== 'AbortError') setState({ data: null, error, loading: false }); });
    return () => ctrl.abort();
  }, [url]);
  return state;
}

Testing

Unit vs integration vs end-to-end tests.theory

Unit: one function or module in isolation, fast, dependencies mocked. Integration: several parts together with real dependencies (API plus a real Postgres and Redis, as in NeoBank's 41 Vitest tests). E2E: the whole system through the UI or public API (Playwright). The test pyramid: many unit tests, fewer integration, fewest E2E. For backend services, integration tests against real databases catch the bugs that matter most (transactions, constraints, locking).

Mocking in Vitest; what should and shouldn't be mocked?theory

vi.fn(), vi.spyOn(obj, 'method'), vi.mock('./module'), fake timers with vi.useFakeTimers(). Mock things you don't own and that are slow or costly (KYC providers, SMS gateways, time). Don't mock your own database layer in integration tests. Use contract tests or recorded responses for third-party APIs. Vitest is Jest-compatible, fast, and works natively with ESM and TypeScript.

TDD: write a failing test, write the minimum code to pass, refactor. For APIs: Fastify's app.inject() or supertest for Express sends requests in-process without a network port. Cover success, validation errors, auth (401/403), tenant isolation (org A can't read org B's data), and edge cases.

Agile, SDLC, Git and code review

Explain Scrum and its ceremonies.theory

Work in sprints (usually 2 weeks). Roles: Product Owner (prioritises the backlog), Scrum Master (removes blockers, guards the process), Development team. Ceremonies: sprint planning (pick and break down stories), daily stand-up (done, next, blockers), backlog refinement / grooming (clarify and estimate upcoming stories), sprint review (demo to stakeholders), retrospective (what went well, what to improve). Artifacts: product backlog, sprint backlog, increment.

Story points, definition of done, velocity.theory

Story points estimate relative effort and uncertainty (Fibonacci: 1, 2, 3, 5, 8, 13), usually via planning poker. Velocity is points completed per sprint, used for forecasting, not for comparing people. Definition of done: code reviewed, tests written and passing, deployed to staging, docs updated, acceptance criteria met.

SDLC models: waterfall vs agile.theory

SDLC phases: requirements, design, implementation, testing, deployment, maintenance. Waterfall does them once in sequence (fits fixed, regulated scope). Agile repeats them in short iterations with working software each sprint and feedback built in. Most teams, including yours, use Scrum or Kanban.

Git: merge vs rebase; branching strategy.theory

Merge keeps history as it happened and adds a merge commit. Rebase replays your commits on top of the target for a linear history; never rebase commits others have already pulled. Strategies: GitFlow (develop, feature, release, hotfix branches), trunk-based (short-lived branches merged to main often, with feature flags). Other commands to know: cherry-pick, revert (safe undo on shared branches) vs reset (rewrites history), stash, bisect (binary search for the commit that introduced a bug).

What do you look for in a code review?theory

Correctness and edge cases first (nulls, concurrency, error paths), then security (auth checks, tenant filter, injection, secrets, PII in logs), performance (N+1, missing index, unbounded queries), tests, readability and naming, consistency with the codebase. Be specific and kind, separate blocking issues from suggestions, and review small PRs quickly.

Clean code practices you follow.theory

Meaningful names, small functions doing one thing, no magic numbers, early returns instead of nesting, consistent error handling, layered structure (route → controller → service → repository), configuration out of code, ESLint and Prettier enforced by Husky, and comments explaining why rather than what.
